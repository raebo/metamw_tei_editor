- **`vendors.js` 3.63 MiB → 1.22 MiB (−66 %), initialer Bundle (`main`-Entrypoint) 4.18 MiB → 1.67 MiB (−60 %).** Root Cause war zweigeteilt:
  1. `LetterViewCode.tsx` importierte `monaco-editor` statisch als Wert (`import * as monaco from 'monaco-editor/esm/vs/editor/editor.api.js'`) nur für ein paar Typen und die `MarkerSeverity`/`setModelMarkers`/`getModelMarkers`-API — obwohl die eigentliche `<Editor>`-UI-Komponente bereits korrekt per `React.lazy(() => import('@monaco-editor/react'))` lazy geladen wurde. Dieser statische Wert-Import zog trotzdem das komplette (mehrere MB grosse) `monaco-editor`-Paket synchron in den Modulgraphen. Fix: der Import ist jetzt `import type { editor } from 'monaco-editor'` (zur Compile-Zeit vollständig entfernt, erzeugt keinen Laufzeit-Import), die tatsächliche Monaco-Instanz kommt jetzt aus dem zweiten Parameter des `onMount`-Callbacks von `@monaco-editor/react` (`(editor, monaco) => ...`) — demselben dynamischen Import, der die Editor-UI schon lazy lädt. **Nebenbefund:** Dabei fiel auf, dass `@monaco-editor/react` in diesem Projekt standardmässig Monaco zur Laufzeit von einem CDN (jsdelivr) nachlädt (kein `loader.config({ monaco })`); die alte statisch importierte Kopie war also vermutlich ohnehin eine vom CDN-geladenen Editor-Realm getrennte zweite Instanz — `setModelMarkers`/`getModelMarkers` liefen also potenziell schon vorher auf der falschen Monaco-Instanz. Die neue Version nutzt garantiert dieselbe Instanz wie der gemountete Editor.
  2. `webpack.config.js`: die einzige `splitChunks`-Cachegroup hatte `chunks: 'all'`, wodurch webpack **jeden** `node_modules`-Treffer — egal ob synchron oder nur per `import()` erreichbar — zwangsweise in dieselbe, eager geladene `vendors.js` gemerged hat. Dynamisch importierter Code (Monaco-Editor-UI, Monaco-Worker) landete dadurch trotzdem im initialen Bundle. Fix: `chunks: 'initial'` — nur synchron erreichbarer `node_modules`-Code landet noch in `vendors.js`; nur-async erreichbarer Code bekommt eigene, on-demand geladene Chunks. Einzeiler, aber hoher Effekt in Kombination mit Fix 1.
  - Verifiziert per `yarn build --env analyze=true` (Vendor-Zusammensetzung vor/nach per Skript aus `dist/bundle-report.html` ausgewertet: `monaco-editor`-Anteil in `vendors.js` sank von 5816 KiB auf 0, ein separater On-Demand-Chunk trägt den Rest der Monaco-Worker-Module) sowie `yarn tsc --noEmit`, `yarn eslint`, `yarn test --runInBand` (alle unverändert grün). **Nicht verifiziert:** kein End-to-End-Test im Browser gegen ein laufendes Backend (in dieser Umgebung nicht verfügbar) — manuelles Nachtesten der Code-Ansicht (XML-Editor-Tab: Öffnen, Tippen, Fehlermarker, Speichern) nach dem Merge empfohlen.

Zeitzonen-Offsets) per Node-Skript gegen die alte `date-fns`-Implementierung verifiziert (exakte Übereinstimmung).
